# Deployment Check Plan

This is a checklist for closing the remaining Phase 5 deployment and verification items. It records acceptance criteria only; no deployment or phase work is started by this document.

| Check | Done means | Real account or hardware needed? |
|---|---|---|
| Neon database migration | On a disposable copy of the production database, inspect for legacy phone/email values beginning with `contact:` before running the backfill, since the current migration treats that prefix as already encrypted. Run migrations and the contact backfill; verify row counts, encrypted-at-rest values, successful application reads/decryption, and that existing encrypted SMTP settings still decrypt. Record the result and any rollback/recovery steps before considering production. | Yes: Neon account/credentials and a database copy. No dedicated hardware. |
| Real email checks | Configure the intended SMTP account, verify the connection, and successfully send and receive representative OTP and application email messages. Confirm sender identity and delivery, and record any provider-specific requirements. | Yes: real SMTP/email account and access to a receiving mailbox. No dedicated hardware. |
| Real WhatsApp checks | Configure the external OpenWA endpoint and API key; verify socket connectivity, link the intended WhatsApp account, deliver a test message to an authorized recipient, and verify STOP handling and the expected connection-status behavior. | Yes: WhatsApp account, external OpenWA service/host, and an authorized test recipient. No special CPU hardware, but the service host is required. |
| Netlify protection | In the deployed path, verify the configured origin secret is enforced end to end: legitimate requests through the intended Netlify proxy succeed, while requests lacking or presenting an incorrect secret are rejected. Confirm the production origin and secret settings without exposing secret values in logs or source control. | Yes: access to the Netlify site/configuration and deployed API environment. No dedicated hardware. |
| arm64 render | On a real arm64 host, launch the production image and Chromium, render the application headlessly, and verify the expected page loads without runtime or architecture errors. Save the check output in the deployment record. | Yes: real arm64 hardware or an arm64 VM. |
| WhatsApp session setup | Confirm OpenWA actually stores its session in persistent storage on the intended host; link the account by QR; restrict socket access to the API and authorized operators; then restart the service and verify the session survives. Document backup/restore and migration steps, including when a QR rescan is needed. | Yes: WhatsApp account and access to the external OpenWA host. Hardware is not inherently required; a persistent host/volume is. |
| Key handling | **Done (key custody):** `SETTINGS_ENCRYPTION_KEY` is stored in a password manager with one offline copy; no key is stored in the repository. Key rotation and re-encryption of recipient contacts and encrypted SMTP settings are still unsupported; do not rotate an in-use key until that path is implemented and verified. | Password manager is in use; no additional account or dedicated hardware needed for the recorded custody setup. |
| Formatting cleanup | Run the repository's formatter check, address any reported formatting issues within the agreed scope, and rerun it to a clean result. Record any intentionally excluded baseline files rather than silently leaving a failing check. | No real account or dedicated hardware. |

Keep credentials and key material out of this plan and all committed files. Record test outcomes and non-secret evidence separately from secrets.
